# 并发上限人工调优指南

## 1. 用途

本文指导维护者在不同机器、ASR 模型和云端账户上调整 Semvideo 的并发上限。
正式 CLI、文件锁和 Agent Skill 上下文门禁已经实现；本文中的“已测试上限”仍只用于
人工调优，不代表可以无界启动 Worker。

并发参数的目标不是“尽量启动更多进程”，而是在以下条件之间取得平衡：

- 提高多个任务的公平性和总吞吐。
- 避免单任务延迟明显恶化。
- 避免 CPU 线程超额订阅、内存不足和磁盘拥塞。
- 避免云端模型 429 限流、供应商过载和费用失控。
- 为系统和 Agent 保留足够资源。

## 2. 必须区分的三种上限

| 名称 | 含义 | 能否直接作为默认值 |
|---|---|---|
| 安全默认值 | 当前 V1 在日常环境中的保守配置 | 是 |
| 建议操作上限 | 继续增加并发通常已无明显收益，或风险开始显著增加的位置 | 只允许人工显式调整 |
| 已测试上限 | 当前机器在有限短测中能够无错误完成的最高档位 | 否；它不是绝对硬上限 |

“8 路短测成功”不等于“正式支持 8 路长视频”。超过已测试上限属于未验证组合，应产生警告而不是被静默接受。

## 3. 当前开发机认证结果

认证环境：

- CPU：AMD Ryzen 9 7940H，8 核、16 逻辑处理器。
- 内存：约 16GB。
- GPU：AMD Radeon 780M；无 NVIDIA CUDA。
- FFmpeg/ffprobe：8.1.2。
- ASR：faster-whisper 1.2.1、CTranslate2 4.8.1、`base/int8`、每 Worker 4 个 CPU 线程。
- 云端模型：硅基流动 `Qwen/Qwen3.6-35B-A3B`；未执行付费压力测试。

| 资源 | 安全默认值 | 建议操作上限 | 已测试上限 | 当前结论 |
|---|---:|---:|---:|---|
| 媒体分析 `media` | `2` | `2` | `8` | 1–8 路总吞吐基本不增长 |
| ASR `asr` | `1` | `2` | `4` | 2 路达到吞吐甜点，4 路无额外收益 |
| 云端模型 `llm` | `2` | 未知 | 未知 | 官方未公开当前账户、当前模型的同时请求硬上限 |
| 软件渲染 `render` | `1` | `2` | `8` | `libx264` 8 路总吞吐低于单路 |

这些值只适用于上述环境。部署到通用 Agent 或未来垂类 Agent 所在的新机器时，应先运行环境诊断并重新认证，不应复制“已测试上限”。

## 4. 调整前准备

1. 选择有代表性的真实视频集合，至少包含长视频、H.264/H.265、可变帧率、快速切镜、长连续镜头、有字幕和无字幕视频。
2. 保持模型、Prompt、ASR Profile、FFmpeg 参数和输入集合不变。
3. 每次只调整一类并发，避免无法确定性能变化来源。
4. 在机器相对空闲时先跑一次基线，再在日常后台负载下复测。
5. 记录调整前的配置，以便立即回退。
6. 云端 LLM 不做无业务价值的付费压力测试；优先读取供应商账户页面额度，再利用正常真实任务逐级观察。

每一档至少记录：

- 成功、失败、取消和中断数量。
- 总墙钟时间与每分钟视频处理量。
- 单任务平均延迟和 P95 延迟。
- CPU 使用率、最低可用内存和磁盘剩余空间。
- Worker 等待各资源槽位的时间。
- FFmpeg 和 ASR 进程峰值工作集。
- LLM 请求耗时、输入/输出 token、429、503、504 和重试次数。
- 实际模型费用。

## 5. 媒体分析上限调整

当前默认：

```text
media = 2
```

Semvideo Skill 在提交、恢复或重试前运行 `scripts/load_context.py`，将有效配置中的
`media` 作为同时活跃处理任务的保守准入上限。应用层在 `submit.lock` 内扣除当前
所有非终态任务并原子校验 `process/resume/retry`；Skill 只读取
`job admission` 的结果编排批次。Agent 只能填满返回的
`available_submission_slots`，任务状态变化后重新加载上下文；不得先把整个目录
展开为大量后台 Worker，再依赖内部分类锁排队。

调整方法：

1. 使用相同视频分别运行 `1`、`2`、`3`、`4` 路。
2. 比较总吞吐，而不是只看“所有进程是否能启动”。
3. 如果增加一档后总吞吐提升低于约 10%，但 P95 单任务延迟明显增加，应回退上一档。
4. 如果最低可用内存低于 2GB、系统持续换页、Agent 响应明显变慢或 FFmpeg 出现资源错误，立即回退。

当前开发机从 1 路增加到 8 路，总吞吐始终约为 51–55 倍实时。因此提高 `media` 的主要意义是让多个任务公平推进，而不是提高整机总吞吐。当前不建议超过 `2`。

媒体预算也覆盖大于 720p 源视频首次生成分析代理的 FFmpeg 转码，并与渲染共享
`ffmpeg_cpu`。媒体分析短测未覆盖大量 JPEG 落盘、感知哈希和九宫格生成。正式
证据流水线的重新认证结果应优先于现有场景过滤短测。

## 6. ASR 上限调整

当前默认：

```text
asr = 1
cpu_threads_per_worker = 4
num_workers = 1
```

当前架构是“每任务一个独立进程”。每个进程内部必须保持 `num_workers=1`，否则实际并行度会变成：

```text
任务进程数 × num_workers × cpu_threads_per_worker
```

调整方法：

1. 先固定 ASR 模型、精度、batch size 和线程数。
2. 使用相同音频测试 1 路和 2 路。
3. 只有 2 路存在稳定吞吐收益且内存充足时，才将操作值提高到 2。
4. 4 路只作为当前 `base/int8` 的已测试能力记录，不作为推荐配置。
5. 更换到 `small`、`medium`、`large`，启用词级时间戳或改变 batch size 后，并发自动回退到 1，重新认证。

当前 30 秒样例结果：

| 并发 | 聚合处理倍速 | 峰值工作集之和 |
|---:|---:|---:|
| 1 | 14.10× | 0.314GiB |
| 2 | 20.32× | 0.628GiB |
| 4 | 20.20× | 1.255GiB |

2 路到 4 路已经没有吞吐收益，因此当前建议操作上限是 2。

## 7. 云端 LLM 上限调整

当前默认：

```text
llm = 2
```

硅基流动公开文档只给出模型类别的 RPM/TPM 范围，没有公开 `Qwen/Qwen3.6-35B-A3B` 在当前账户上的同时在途请求数，也没有公开当前账户的精确额度。多个 API Key 不能叠加同一账户、同一模型的限额。

人工调整前：

1. 登录硅基流动模型广场。
2. 查看当前账户等级和该模型当时显示的 RPM、TPM，以及页面是否单独给出并发数。
3. 将账户值写入本地未跟踪配置，不提交仓库。
4. 统计正常真实任务中单个九宫格请求的 token 分布和耗时。

调整方法：

1. 从 2 开始，每次只增加 1。
2. 使用有业务价值的真实视频任务观察，不发送纯压力请求。
3. 一旦出现 429，立即停止提高；同一供应商、账户和模型的所有 Worker 进入共享冷却。
4. 对 429 使用带随机抖动的指数退避；失败请求也可能计入 RPM，不能密集重试。
5. 503/504 按供应商过载处理，与账户 429 限流分开统计。
6. 如果正常任务观察到 token 成本或 P95 延迟明显异常，即使没有 429 也应回退并调整证据 Profile；V1 不用单任务 token 硬预算自动中止。

在没有账户精确额度且不执行付费压力测试时，无法验证一个诚实的固定最大并发。因此 `2` 是应用安全默认值，不是供应商保证的上限。

Agnes `agnes-2.5-flash` 使用独立的模型提供商配置档：总上下文固定为
`524288` tokens，默认输出保留 `8192` tokens，因此默认输入预算为
`516096` tokens；同时在途请求上限固定为 `2`。512K 是单请求总上下文能力，
不能据此提高并发。公开 Free/default 账户的文本请求参考值为 20 RPM，但 RPM
也不能直接换算成同时请求数，因此当前配置档不允许把 Agnes 的 `llm` 提高到 2
以上。可显式降低为 1；更高账户等级不自动改变该安全上限。

## 8. 视频渲染上限调整

当前默认：

```text
render = 1
```

调整方法：

1. 软件编码与硬件编码必须作为不同 Profile 分别认证。
2. `libx264` 先比较 1 路和 2 路的总吞吐、单任务延迟、温度和输出可解码性。
3. 如果需要多个长任务公平推进，可以显式提高到 2。
4. 不建议把短测成功的 8 路配置为日常值；开发机上 8 路总吞吐比单路下降约 8.5%。

本机 `h264_amf` 曾在 8 路短测中成功，但没有进行等质量、等码率和长时间稳定性比较。它只能作为可选 Profile 候选，不能自动替代 `libx264`。

## 9. 跨类别共享资源

分类槽位不代表物理资源彼此独立。`media=2` 与 `render=1` 可能同时形成三个 CPU 密集型 FFmpeg 进程。本机混合短测相对对应单类基线增加约 61.8% 墙钟时间。

V1 已确认：

```text
ffmpeg_cpu = 2
```

Worker 应先取得共享 `ffmpeg_cpu` 槽，再取得 `media` 或 `render` 分类槽，并始终遵守同一锁顺序以避免死锁。未来使用 AMF 等硬件编码时，应单独定义 GPU 预算，不能继续占用或绕过 CPU 预算而不做测量。

## 10. 回退条件

出现下列任一情况时，立即回退到上一档：

- 任何输入出现此前没有的资源不足或进程启动失败。
- 总吞吐没有提高，但 P95 单任务延迟增加超过约 25%。
- 可用内存持续低于 2GB或出现明显系统换页。
- Agent、终端或其他本机程序明显失去响应。
- 429 持续出现或重试量明显增加。
- 模型费用超出预期。
- FFmpeg 输出无法解码、时间范围错误或导出质量发生变化。

回退后保留失败档位的测试记录，不把它删除或覆盖；记录机器、模型、Profile、输入集合和失败原因。

## 11. 重新认证触发条件

发生以下变化时，原认证上限失效：

- 更换 CPU、内存、磁盘或运行机器。
- 增加 NVIDIA GPU 或改变 CUDA/cuDNN。
- 升级 Python、FFmpeg、PyAV、faster-whisper 或 CTranslate2。
- 更换 ASR 模型、精度、batch size 或线程配置。
- 更换视频编码器、preset、分辨率或质量参数。
- 更换云端供应商、模型、账户等级或请求证据规模。
- Agent 从通用环境迁移到垂类环境，并与其他高负载工具共享机器。

Agent Skill 只能通过正式 CLI 读取诊断、调整本地配置、提交和观察任务；不得直接编辑任务状态文件或绕过并发控制。
