# 多模态预筛请求与成本设计

## 结论

“质量预筛”不应默认等于一次云端多模态请求。建议把预筛拆成两层：

1. **本地零 VLM 成本预筛**：元数据、来源许可/版权规则、内容哈希与感知哈希、重复检测，以及通过 `ffprobe`、OpenCV 等得到的分辨率、码率、时长、帧率、宽高比、黑帧/冻结帧等技术质量指标。
2. **云端视觉预筛**：只判断本地规则无法可靠回答的内容，例如画面是否符合目标语义、主体是否真实出现、镜头是否具有可剪辑价值、遮挡是否严重等视觉可用性。

因此，元数据、版权、重复和基础技术质量本身**不产生额外 VLM 请求**。云端调用只发生在候选通过本地预筛之后，并应与后续片段语义标注尽量复用，避免同一素材被视觉模型分析两次。

SiliconFlow 官方文档显示，Qwen3-VL 支持图像和视频输入；Qwen 系列图像在 `detail=low` 时约按 256 token/张计入输入。视频最终抽帧数为：

```text
frames = min(fps × 视频时长秒数, max_frames)
```

官方的一般建议是 `max_frames=8–16`、`fps=1–2`。参见 [SiliconFlow 多模态模型文档](https://docs.siliconflow.cn/cn/userguide/capabilities/multimodal-vision)。

## 推荐的三级漏斗

### 第 0 级：本地确定性预筛

不调用云端模型，先排除：

- 来源、许可或使用范围不允许的候选；
- URL、平台 ID、文件哈希或感知哈希重复的候选；
- 时长、分辨率、码率、帧率、编码格式等不达标的候选；
- 可由本地图像算法识别的黑帧、冻结帧和明显损坏；
- 标题、描述和标签与查询完全无关的候选。

版权状态应依据来源平台、许可证和采集记录判断，而不是让视觉模型“看画面猜版权”。

### 第 1 级：6 帧低成本视觉预筛

每个候选在本地均匀或按场景变化抽取 6 帧，以一个请求提交给 Qwen3-VL，要求只返回短 JSON，例如：

```json
{
  "relevant": true,
  "usable": true,
  "score": 0.82,
  "reasons": ["主体清晰", "存在可用广角镜头"]
}
```

这个请求同时完成“语义相关性”和“视觉可用性”判断，不再另发所谓的质量检查请求。

### 第 2 级：按需升级

仅对以下候选升级为 8–16 帧或完整 `video_url` 分析：

- 6 帧结果不确定；
- 候选价值很高，但关键动作可能未被采样；
- 已准备下载/落库，需要更细的时间定位；
- 第 1 级与元数据判断明显冲突。

不要让所有搜索结果直接进入完整视频分析。若落库工具本身会调用同一个视觉模型做切分摘要，则应把第 1 级结果和抽帧缓存传给落库流程，或直接把视觉预筛合并到落库分析，避免重复计费。

## 6 帧方案的成本

以当前官方价格页所列 `Qwen/Qwen3-VL-8B-Instruct` 为例：

- 输入：¥0.50 / 1M tokens
- 输出：¥2.00 / 1M tokens

价格可能调整，实施时应从 [SiliconFlow 官方价格页](https://siliconflow.cn/pricing) 核对，不要硬编码。

设：

- 6 张 `detail=low` 图像：`6 × 256 = 1536` 个视觉输入 token；
- 文本提示和候选元数据：`P` 个输入 token；
- 短 JSON：`O` 个输出 token。

则单候选估算成本为：

```text
单候选成本（元）
= ((1536 + P) / 1,000,000 × 0.50)
  + (O / 1,000,000 × 2.00)
```

若按 `P = 200`、`O = 120` 估算：

```text
输入成本 = 1736 / 1,000,000 × 0.50 = ¥0.000868
输出成本 =  120 / 1,000,000 × 2.00 = ¥0.000240
单候选合计                              ≈ ¥0.001108
100 个候选                              ≈ ¥0.1108
```

这只是预算估算。最终应保存 API 响应中的 `usage.prompt_tokens`、`usage.completion_tokens` 和实际金额，按真实 usage 汇总候选、批次、查询计划和整个任务的成本。

## 进一步压低成本

### 缓存

使用以下内容生成稳定缓存键：

```text
源内容哈希
+ 抽帧策略版本
+ 帧内容哈希
+ 模型名
+ prompt/schema 版本
+ detail
```

相同候选在递归搜索、重试或不同查询计划中再次出现时，直接复用视觉判断。仅 URL 相同不足以作为缓存键，因为源内容可能被替换。

### 批处理

一个候选的 6 帧应放入同一请求，而不是发 6 次请求。多个候选可以用受控并发或应用层小批次处理，以减少连接开销；但若计费仍按输入/输出 token，合并请求通常**不会降低 token 费用**，还会增加候选映射、失败重试和上下文污染的复杂度。

### Contact sheet

可把 6 帧在本地拼成一张 contact sheet，再以一张 `detail=low` 图片提交。按 Qwen 的低清规则，视觉输入可从约 `1536` token 降到约 `256` token：

```text
Contact sheet 单候选估算
= ((256 + P) / 1,000,000 × 0.50)
  + (O / 1,000,000 × 2.00)
```

按同样的 `P = 200`、`O = 120`：

```text
单候选 ≈ ¥0.000468
100 个候选 ≈ ¥0.0468
```

代价是 6 个子图会在 `448×448` 画布内变小，细节、文字、小主体和遮挡判断会变差。因此 contact sheet 适合第一轮粗筛；低置信度或高价值候选再升级为 6 张独立图片或视频请求。

## 建议的默认策略

```text
所有候选
→ 本地许可、元数据、哈希、ffprobe/OpenCV 预筛（0 次 VLM）
→ 入围候选用 1 张 contact sheet 做粗筛（1 次低成本 VLM）
→ 低置信度/高价值候选用 6 张独立低清帧复核（可选 1 次 VLM）
→ 仍需时间定位的少数候选升级为 8–16 帧或 video_url（可选 1 次 VLM）
→ 复用结果进入切分落库
```

成本预算应设置为任务级硬上限，并同时记录：

- 本地预筛前候选数；
- 进入 contact sheet、6 帧复核和完整视频分析的候选数；
- 各层通过率与有效落库率；
- 缓存命中率；
- 每层真实 token usage 和人民币成本；
- 每个有效落库片段的平均视觉分析成本。

这样，“质量预筛”不会无条件增加一轮云端请求；只有视觉语义确实需要模型判断时才花费，并可通过漏斗、缓存和分级升级把成本集中在最有希望的候选上。
